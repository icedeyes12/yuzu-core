# Yuzu Companion v4.3 — Architecture Roadmap

Status: living roadmap. Edit via PR; archive major versions under `docs/archive/`.

## Vision

Transform Yuzu Companion from a single-host AI companion into a distributed AI platform
with isolated execution environments.

## Core Principles

1. AI never executes directly on the host.
2. Every user owns an isolated workspace.
3. Terminal execution is separated from Yuzu Core.
4. Yuzu Core orchestrates, never performs privileged work.
5. Sandboxes are disposable, reproducible, and independently resettable.

## Infrastructure Overview

```text
Cloudflare Pages (landing)
        |
yuzuki.space
        v
companion.yuzuki.space
        |
Cloudflare Tunnel
        v
   titit-dev            <- orchestration host (current Termux device)
FastAPI
PostgreSQL
Memory / Auth / LLM / Tool Dispatcher / Sandbox Manager (client)
        |
Private Network (Tailnet / SSH)
        v
   sandbox nodes (titit-3, worker phones, VPS...)
yuzu-sandboxd
PRoot / terminal / python / git / user workspaces
```

## Host Responsibilities

### titit-dev (orchestrator only)

Runs: FastAPI, PostgreSQL, authentication, memory (graph), AI, tool dispatcher,
sandbox manager client.

Never: execute user shell, execute Python, expose host filesystem.

### Sandbox node (e.g. titit-3, worker phones)

Runs: PRoot, terminal runtime, Python runtime, git, per-user workspaces.

No PostgreSQL, no Yuzu Core.

## Sandbox Runtime: yuzu-sandboxd

Small dedicated service per node. Responsibilities only:

create, start, stop, execute, open terminal, destroy, reset, stream logs, status.

→ the historical draft is preserved in `docs/archive/sandboxd-spec-2026-08-06.md`; this roadmap section is not the current runtime contract.

## Communication

Phase 1: SSH (simple, stable, debuggable). Yuzu -> SSH -> sandboxd.

Phase 2: HTTP/WebSocket API on sandboxd.
  POST /sandbox/create
  POST /sandbox/execute
  POST /sandbox/reset
  GET  /sandbox/status

Tailscale is the private transport (Android-level, no Termux-side tailscaled).
Yuzu always speaks HTTP (phase 2) or SSH (phase 1) over tailnet IPs; never treats
Tailscale as the application protocol.

## Node Bootstrap

install python -> install yuzu-sandboxd -> register node -> heartbeat -> ready.

Current node roles:
- Node A (always-on candidate, future Phase-2 infrastructure work)
- Node B, C, D (on-demand worker nodes)

## Sandbox Template

Minimal rootfs template, copied lazily at first terminal open:

Debian minimal, python, git, sqlite, curl, bash, ca-certificates.

NO: compiler, postgres, node, rust, ffmpeg.

## User Sandbox Lifecycle

- On register: DB row only (no rootfs).
- On first terminal open: create rootfs -> copy template -> workspace/ -> metadata -> ready.
- Lazy initialization keeps registration cheap.

Layout on each node:

```text
sandboxes/
  template/
  users/<sandbox-id>/
    rootfs/
    workspace/
    home/
    metadata.json
    state.json
```

## Sandbox Manager API (internal)

create / destroy / reset / execute / attach / detach / snapshot / status / heartbeat.

## Web Terminal

xterm.js -> WebSocket -> PTY -> sandboxd -> bash.
No polling. Interactive (vim, nano, python, htop, less).

## Tool Migration

Move into sandbox: terminal execution, python execution, shell, git, file
editing, user sqlite DBs, package installation, project generation, code execution.

Stay in Yuzu Core: authentication, memory, chat, embeddings, postgres,
scheduler, notification, admin, billing (future).

## Frontend (v4.3 retouch)

Sidebar: Chat / Files / Terminal / Memory / Project.
Workspace becomes the primary concept; terminal is no longer a popup.

Future view:

```text
Workspace
  Chat / Files / Terminal / Projects / AI
```

Agent and user share the same workspace: an agent-written file appears
immediately in Files and opens in Terminal.

## Security

Yuzu Core never holds a shell. Flow:
User -> LLM -> Policy -> Sandbox Manager -> sandboxd -> PRoot.
A sandbox crash must never take down Yuzu Core.

## Long-term: Node thinking

Treat worker devices as "Node" resources, not as special-case hardware.
Yuzu Core asks: Node A idle / busy / offline — and picks. v4.3 design must
allow adding a VPS or mini-PC without changing Yuzu Core's model of a sandbox.
