# Provider Identity System

The frontend provider identity contract lives in `static/js/visual-registry.js` and is exposed as `window.VisualRegistry`. It is presentation-only: provider IDs, model selection, API requests, and runtime behavior remain unchanged.

## Contract

Every provider entry has the same fields:

- `id`: backend/provider identifier used for lookup.
- `displayName`: full label shown to users.
- `shortName`: compact human-readable label.
- `family`: provider family or vendor grouping.
- `logo`: future asset path; `null` means no dedicated logo is registered.
- `fallbackLogo`: short placeholder mark used when `logo` is unavailable.
- `accentColor`: optional provider accent; keep `null` until an approved, accessible asset palette exists.
- `badge`: standardized identity classification (`official`, `local`, `custom`, or `unknown`).
- `supportsDark`: whether the identity asset is approved for dark surfaces.
- `custom`: whether the provider is user-configured/custom.
- `experimental`: whether the provider is experimental.
- `deprecated`: whether the provider is retained for compatibility but deprecated.

Unknown IDs resolve to the immutable `unknown` fallback instead of requiring UI conditionals.

## Ownership and usage

`VisualRegistry` owns provider display metadata. Config provider cards consume registry entries for display name, family, badge, and placeholder. Provider IDs still come from the API and remain the source of runtime configuration.

UI icons, provider logos, brand assets, and status visuals are separate concepts. Provider logos must not be replaced with generic UI icons or emoji.

## Adding a provider

1. Add one entry to `providerDefinitions` in `static/js/visual-registry.js` using the exact backend provider ID.
2. Fill every contract field deliberately; use `logo: null` and a two-character `fallbackLogo` until an approved logo asset exists.
3. Assign an existing badge classification unless a new classification is explicitly justified.
4. Run Biome, `node --check` on changed JavaScript, and `git diff --check`.
5. Verify the config provider card visually before committing.

Do not add provider-specific `if`/`switch` branches to components. Use `VisualRegistry.getProvider(id)`.

## Logo and accent changes

Register a logo path only after placing the owned asset under `static/assets/logos/providers/` and checking light/dark contrast. Keep the fallback available for load failure. `accentColor` is metadata for future presentation work; it must not be the only carrier of status or accessibility meaning.

Provider assets should use semantic CSS treatment from `visual-language.css`; do not add inline SVG or emoji per provider.

## Placeholder rules

Placeholders are generated by the shared `.provider-identity-placeholder` component style. They use the registry's `fallbackLogo`, semantic surface/border/text tokens, and stable sizing. A placeholder is preferred to an invented or inconsistent provider mark.

## Badge rules

Badges are semantic labels, not decoration. Use the existing classifications consistently, keep the text visible, and style through the shared `.provider-identity-badge` classes. Do not use badge color as the sole indicator of provider state.
# Provider Identity System

## Contract

`static/js/visual-registry.js` is the single frontend source of truth for provider presentation. Every entry exposes:

- `id`: stable backend/provider key.
- `displayName`: full user-facing name.
- `shortName`: compact label for constrained layouts.
- `family`: provider/vendor grouping.
- `logo`: approved provider mark, or `null` until an owned asset exists.
- `fallbackLogo`: registry-owned placeholder text used when `logo` is absent.
- `accentColor`: optional provider accent for non-essential decoration only.
- `badge`: `Official`, `Community`, `Custom`, `Experimental`, `Deprecated`, or `Preview` when applicable.
- `supportsDark`: whether the registered mark is safe on dark surfaces.
- `custom`, `experimental`, and `deprecated`: lifecycle/capability flags.

The registry also exposes `getProvider(id)` and `listProviders()`. Unknown IDs resolve to a neutral fallback entry rather than a provider-specific guess.

## Ownership

- `static/js/visual-registry.js`: provider metadata and lifecycle flags.
- `static/css/components/visual-language.css`: placeholder and badge presentation.
- `static/assets/icons/`: generic UI icons only.
- `static/assets/logos/providers/`: provider marks only.
- `static/assets/logos/brands/`: login or external brand assets only.
- `static/assets/illustrations/`: non-interactive illustrations.
- `static/assets/status/`: status visuals.

Provider logos are not generic UI icons. Do not add emoji or ad-hoc inline SVG as a provider mark.

## Adding a provider

1. Add one complete entry to `providerDefinitions` with the backend provider ID.
2. Use a neutral `fallbackLogo` until an approved owned logo is available.
3. Assign the correct `family`, lifecycle flags, and badge.
4. Add the asset under `static/assets/logos/providers/` only when it has a clear owner and light/dark treatment.
5. Run Biome, `node --check`, and the frontend smoke test.

## Changing identity

Change `logo`, `accentColor`, or `supportsDark` only in the registry. Components must consume registry metadata and must not recreate provider mappings. Provider accents are decorative and must never be the only indicator of state or meaning.

## Placeholder and badge rules

Placeholders use the shared `.provider-identity-placeholder` styles and registry fallback text. Badges use semantic status/accent tokens through the shared badge classes. Keep them compact, readable, and independent from provider logo availability.
